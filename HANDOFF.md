# Handoff brief — Stadia controller firmware RE, Claude → Gemini

Written 2026-08-17 at the end of a long continuous Claude session (git log shows it as "sessions 6–23"). The owner is switching to Gemini for the next several work cycles to conserve Claude usage. This doc explains the **process** that produced the last ~18 commits of steady progress, and the **current state**, so a different model can pick this up cold and keep the same cadence. ## The one-paragraph summary

This is a large, open-ended reverse-engineering project (decompile+document a ~5,000-function embedded ARM firmware image to source-reconstruction quality) that doesn't fit in one context window. The way it's actually gotten done: the orchestrating session never decompiles anything itself — it reads the two tracking docs, dispatches exactly one Ghidra-touching subagent plus one independent-verification subagent per "wave," waits for both, commits the result with a detailed message, updates `CLAUDE.md`'s status section if something notable happened, and picks the next wave's targets from the tracking docs. Repeat. That loop is the whole method. It has run ~20 times today and produced real, checkable progress every time.

> **Update (2026-08-17) — the process is now a two-model pipeline.** Decompilation and QA have been split across two independently-budgeted autonomous loops that alternate via git: **Gemini owns Ghidra/decompilation, Claude owns QA/verification.** If you're starting a loop, read **`PIPELINE.md`** (the turn protocol + the ~45-min idle-poll wait rule) and your role file — **`PIPELINE-GEMINI-GHIDRA.md`** or **`PIPELINE-CLAUDE-QA.md`** — instead of running the single-orchestrator loop below. The section below is retained as the reference for *how a decompile wave is done* (the Gemini role links back to it), and the rigor rules further down apply to both halves.

## The loop, in detail

1. **Read `CLAUDE.md` in full.** It has the Ghidra tooling commands, the known naming traps, and — most importantly — a "Current status & next targets" section that is the living, prioritized to-do list. Trust it over your own assumptions; it's been kept current after every wave.
2. **Read `analysis/bruce-decompile-status.md` in full.** This is the master data-driven tracker: exact coverage percentages, a per-source-file table of what's attributed-but-not-yet-decompiled (§3a — the cheap wins, ranked by remaining bytes), and a ranked list of large unattributed address ranges still worth investigating (§3b). Pick your next targets from here, not from memory or guesswork — it gets regenerated periodically precisely so this is reliable.
3. **Dispatch exactly one Ghidra-touching subagent per wave.** `analysis/ghidra/bruce.rep` is a single-writer, file-based Ghidra project. Two concurrent `analyzeHeadless -process` invocations *will* conflict — this happened once (see "Incidents" below) and cost real time to recover from. The hard rule that came out of it: **never launch two agents in the same wave that both plan to touch Ghidra.** One Ghidra agent, full stop.
4. **Pair it with one non-Ghidra subagent, working purely from files already on disk.** Three flavors, rotate between them based on what's stalest/highest-value:
   - **QA / adversarial verification** of the previous wave's claims — re-read the actual decompiled `.c` files and independently check specific asserted facts (byte constants, caller counts, structural claims) rather than trusting the write-up. This has been the single highest-value pattern in the whole project: it has caught a real, fixable error in **almost every single pass** — misattributed VID/PID tables, wrong register claims, overstated confidence, arithmetic mistakes, a completely wrong "no caller found" claim that turned out to have a confirmed unconditional call path from `main()`. Do not skip this. Findings get corrected in place in the relevant `analysis/*.md` file.
   - **Regenerating `analysis/bruce-decompile-status.md`** — it drifts stale after a few waves of decompiling. It documents its own exact join methodology at the bottom (join on 8-hex address, not name; `bruce_functions.csv`'s name column is stale for attributed functions; exclude non-census carve-out decomp files) — follow it exactly, it's been refined across several regenerations to avoid subtle bugs.
   - **Documentation consolidation** — writing up already-decompiled-but-undocumented functions, or merging findings that landed in the wrong doc into the right one.
5. **Both subagents report back a short summary.** Read them, sanity-check for internal consistency (the QA agent's corrections vs. the other agent's claims), then:
6. **Checkpoint with git.** `git add -A`, then a commit with a detailed message in the established style: explain *what was found and why it matters*, not just *what files changed*. Look at `git log` on this branch for many examples of the expected depth. End every commit message with `Co-Authored-By: <your model name> <noreply@anthropic.com>` (adjust the name/email convention to whatever's appropriate for you — the existing convention in this repo has evolved from "Claude Opus 4.8" to "Claude Sonnet 5" as the actual authoring model changed session to session; be honest about which model actually did the work). **Commit after every single wave** — don't let multiple waves' work pile up uncommitted, and don't ask the user before committing on this branch (that permission is effectively established by ~20 prior same-pattern commits; work happens on `firmware-re`, never `main`, and this repo has no shared collaborators to worry about).
7. **Repeat.** Pick the next wave's targets from the (now-current) tracking docs.

### Hard rules, learned from real incidents

- **One Ghidra agent per wave, no exceptions**, even with "check if it's busy first" instructions to a second agent — that heuristic does not reliably converge (an agent can loop indefinitely re-checking rather than proceeding, or worse, both agents can race). Serialize explicitly by simply never dispatching two in the same wave.
- **Never pass multiple Ghidra addresses via a shell variable** (`$ADDRS`, `$(...)`) — this silently mangles the argument list into one bad argument and Ghidra throws a `NullPointerException`. Always type addresses as literal space-separated tokens directly in the `analyzeHeadless` command line. Works fine up to at least 25–30 addresses per invocation.
- **`getImageBase()` returns 0`** for the raw `BinaryLoader` import this project uses — use `getMinAddress()` for the real load address if writing new Ghidra scripts.
- Subagents given only a soft "wait if busy" instruction can get stuck in an unproductive check-loop and need a direct, explicit override message from the orchestrator ("I have personally verified via `ps aux` and lock-file checks that Ghidra is free — stop checking and proceed now") to break out. If you see this happening, intervene directly rather than waiting for it to self-resolve.

## Rigor rules for decompilation write-ups (added after the sessions 24–28 adversarial audit — read this before every wave)

An independent, byte-level audit re-checked all 120 functions decompiled in sessions 24–28 against the raw flash image. **Verdict: the work is trustworthy and should continue** — every *fabrication*-class risk was absent (no invented addresses, no invented functions, no invented strings; all 120 functions exist at their stated addresses and the 448/448-attributed milestone is real). But a consistent, correctable error profile emerged: **9 substantive errors in ~103 checked claims, and every one was a wrong label attached to correct bytes, in the exact spot where the write-up reached *past* a leaked string.** The QA wave itself *reinforced* two of the errors instead of catching them. The rules below target those failure modes literally. Precision here is the entire value of the work — "8/10, mostly right" is not "recompile-grade."

**The one principle behind all of it:** a leaked `__FILE__` string, a verbatim log/format string, or an RPC dispatch-table entry is *hard evidence* — lean on it, quote it, and the identification will be right (this is why ~94 of ~103 audited claims held up perfectly). The instant a claim goes *beyond* what a string proves — naming a peripheral, an enum, an API, a struct field, a function's size, or the behavior of an unnamed function — it must be independently grounded in bytes, or it drifts. All 9 confirmed errors were in that extrapolation zone.

Concrete DO / DON'T, each anchored to a real sessions 24–28 miss:

1. **Peripheral register bases — verify against the SoC memory map AND grep the repo. DON'T name one from memory.**
   - Miss: `0x400D8000` was labeled the "OCOTP peripheral base" in `heap_5_improved.c`; OCOTP is actually `0x401F4000` — a fact *this same repo states correctly twice* (`bruce-misc-functions.md`'s BEE section, `analysis/device-probe-log.md`). `0x400D8000` is the CCM_ANALOG/ANATOP block.
   - Rule: before naming any `0x40xxxxxx` / `0x60xxxxxx` literal as a peripheral, (a) confirm the base against the i.MX RT106x memory map, and (b) `grep -rn` that base across `analysis/` — if it is already named anywhere, match that name or resolve the contradiction *before* writing. A base that recurs many times across the image is a shared block (clock/analog/GPIO/SNVS), not a one-shot fuse read.

2. **Function size / boundaries — check for tail-branches and census overlap. DON'T trust Ghidra's reported size blindly.**
   - Miss: `heap_5_improved__600521b8` was written up as a clean 254-byte `vPortDefineHeapRegions`. The real function is ~52 bytes and ends in a `b.w 0x600cc71c` tail-branch to the actual init body; the 254-byte census extent *overlaps four other census functions*, and the headline `0x80000000` xBlockAllocatedBit detail lives at the branch target, not at `0x600521b8`.
   - Rule: before quoting a size, check (a) does the disasm/decomp end in a `b.w` into a different address range, and (b) do any rows in `bruce_functions.csv` *start inside* `[addr, addr+size)`? Either means the boundary is a Ghidra artifact (the same failure class as the known `FUN_601054dc` jump-table corruption) — document the real extent and flag the artifact; never present the inflated size as fact.

3. **Unnamed (`FUN_*`) functions and hardware-effect claims — stay strictly inside the evidence. This was the only true hallucination found.**
   - Miss: `FUN_6007f7a0` was written up in `bruce-audio-subsystem.md` as a keyframe sequencer that "interpolates steps and drives PWM/haptics." It is actually the `"UxPatternLog"` diagnostic-RPC serializer (proven by the dispatch-table entry at `0x6013cebc` → handler `0x6007f7a1`) — no interpolation, no hardware driving — and the mislabel *contradicts* `bruce-log-buffer.md`, which already lists it correctly.
   - Rule: for a function with no `__FILE__` attribution, assign no behavioral identity beyond what a string, constant, or dispatch-table entry directly proves. NEVER claim a hardware effect (PWM/LED/haptic/DMA/I2C) unless a store to that peripheral or a call to a known driver appears in the decomp. Before writing up anything reachable from an RPC dispatch table, cross-check the dispatch tables and `bruce-log-buffer.md` first.

4. **Sibling-value branches — derive which-is-which; DON'T assume ordering. This is the most dangerous class because a swap still reads as correct.**
   - Misses: `tasn_utl.c` labeled the `null_tt` / `default_tt` return templates backwards; (earlier, session 23) `p_x25519_asn1.c` swapped the priv vs pub roles.
   - Rule: whenever two branches return sibling values (default vs null, priv vs pub, r vs s, min vs max), pin *each* from BOTH its struct offset and the library's documented semantics, and cite the offset for each. Never infer the roles from branch order.

5. **Enum / error-lib / API names — map through the actual enum; distinguish sibling APIs by behavior.**
   - Misses: `obj.c` labeled `ERR_LIB` value 8 as "ASN1" (8 = OBJ; ASN1 = 12 — a value the same doc uses correctly elsewhere); `buf.c`'s `BUF_MEM_reserve` was called `BUF_MEM_grow` (grow writes `length` and memsets — reserve does neither, and the QA "fix" reinforced the wrong name); `timers.c`'s `prvSwitchTimerLists` was called `prvProcessExpiredTimer` (which has no loop and no list swap).
   - Rule: never guess an enum value's name — map it through the enum table. Distinguish sibling library functions by their *defining* behavior and cite it (does it write `length`? memset? loop? swap lists?).

6. **Struct fields — only claim a field is set if there is an actual store to that offset.**
   - Miss: `bio.c`'s `BIO_new` was said to set `init=1`; `init` lives at `+4` and is left 0 (only `references@+8` and `shutdown@+0x18` are set to 1).
   - Rule: cite the offset for every field you claim is initialized; if there is no `str` to that offset in the decomp, don't claim it.

7. **Self-reported stats — compute them from the census join, don't estimate.**
   - Misses: session 24 claimed "29 functions" (28 decomp files were added); session 27 claimed "2,752 bytes" (the 25 files sum to 3,116); `bruce-decompile-status.md` §1's top-line still reads "80 of 139 / session 24" while §3a correctly shows zero remaining.
   - Rule: derive each wave's function count and byte total by joining the newly-added `analysis/decomp/*.c` files against `bruce_functions.csv` (address-join, 3rd column = size) — never hand-count. When you touch `decompile-status.md`, either fully regenerate it per its own bottom-of-file methodology or explicitly mark which sections are stale; never leave §1 contradicting §3a.

8. **Jump-table and adjacent-split boundary artifacts — identify switch interior fragments. DON'T count or name jump-table case bodies as distinct functions.**
   - Miss: SDP's `sdpu_get_len_from_type` (`0x600bfb4c`–`0x600bfc10`, ~196B) was split by Ghidra into 3 adjacent census entries (14B @ `0x600bfb4c`, 8B @ `0x600bfb5a`, 174B @ `0x600bfb62`) at the jump-table boundary. `0x600bfb5a` and `0x600bfb62` were mistakenly given fabricated names (`sdpu_extract_attr_seq_len`, `sdpu_process_attribute_rsp`) and counted as separate functions to reach an inflated "36/36 = 100%".
   - Rule: (a) If a function ends in an indirect branch (`ldr.w pc, [rN, rM, lsl #2]`, `TBB`, `TBH`) or its decompiled `.c` contains warnings like `"Could not recover jumptable"` / `"Treating indirect jump as call"` / reads uninitialized register inputs (`unaff_rN`, `in_rN`, `in_CY`, `in_ZR`), check if immediately adjacent following entries in `bruce_functions.csv` are interior case bodies of the same switch.
   - (b) Treat the entire span as ONE function. Do not invent distinct API/subsystem names for switch fragments, and do not count case fragments as independent functions toward subsystem completion tallies.

9. **Spec-identity labels in crypto/protocol code — verify defining functional behavior, NOT just pattern matches. DON'T label wrappers as primitives.**
   - Misses: SMP's `0x600c1204` was labeled "f6 check-value generation" (f6 is a DHKey-check MAC; `0x600c1204` is the `g2` numeric-comparison orchestrator calling `0x600c12b0`, thresholding $\le 999999$ via `DAT_600c12ac = 0xF423F`, and firing event `0x22`); `0x600c0e7c` was called a distinct "f5 key generation" (it makes a byte-identical call to `FUN_600f0ac8` with identical arguments as the f4 wrapper, differing only in state byte 3 vs 4; real f5 takes salt/counter/addresses/lengths and emits two 128-bit outputs MacKey+LTK); EC modular field routines (`0x600c89e0`, `0x600c8a54`, `0x600c8acc`) operating on a single scalar in $\mathbb{F}_p$ were labeled "Jacobian projective point arithmetic" (real point operations operate on multi-coordinate $(X, Y, Z)$ tuples with chains of field muls/sqrs and reside in callers `0x600fffbc`/`0x600ffe42`); L2CAP `0x600bbb2c` was called a "CID allocator" when it is an Echo Response builder (`FUN_600bb7e4` with opcode 9); BTU `0x600a9e74` was called a "credit processor" when it is a parameterless struct `memset` initializer.
   - Rule: (a) Before applying a specific named cryptographic or protocol primitive label (e.g. SMP $f4, f5, f6, g2$, EC point vs field, specific HCI opcode, L2CAP signaling opcode), verify the defining structural behavior:
     - $f5$: Must produce two 128-bit outputs (MacKey + LTK) and use a key generation salt/counter.
     - $f6$: Must compute the 128-bit DHKey-check MAC.
     - $g2$: Must compute 6-digit numeric comparison passkey reduced modulo $10^6$.
     - EC Point Op: Must manipulate 2-3 projective coordinates $(X,Y,Z)$ with multiple field multiplications/squarings.
     - EC Field Op: Operates on 1-2 multi-precision scalar operands with a single addition/subtraction/shift and modular reduction.
     - L2CAP PDU: Opcode 0x08 = Echo Req, 0x09 = Echo Rsp; check payload offsets before assuming CID allocation.
   - (b) **Rejection rule**: If two functions claimed to be different spec primitives make byte-identical library calls with the same arguments, reject the distinct primitive label—they are state machine wrapper branches into the same underlying helper (which may reside in un-decompiled blocks like `0x600f0xxx`).
   - (c) **Commit & milestone honesty**: Never claim in commit messages or headlines that "command PDU serializers" or "builders" were decompiled unless actual wire opcode bytes are stored into packet buffer offset 0 (`buffer[0] = opcode`). Do not report "100% / N of N" for a subsystem until boundary splits (Rule 8) have been audited and de-duplicated.

**The QA/verification wave is now the single highest-leverage rule, because in this audit it *reinforced* two errors (it endorsed the OCOTP misID and the `BUF_MEM_grow` name) rather than catching them.** A QA pass that paraphrases the write-up is worse than none. Every QA wave MUST:
   - **Re-derive each claim from the raw bytes/strings independently** — treat "the write-up says X" as a hypothesis to *refute*, never as an established fact. Dump the bytes yourself (`file_offset = flash_addr − 0x60040000`, verified) and confirm.
   - Run this fixed checklist every pass: (1) every peripheral base re-resolved against the memory map **plus** a repo-wide `grep` for a conflicting existing name; (2) every enum / error-lib / reason value re-mapped through its enum; (3) every priv/pub, default/null, r/s, min/max branch assignment re-derived from offsets; (4) every quoted function size checked for tail-branch/overlap artifacts; (5) every jump-table boundary checked for adjacent split fragments / uninitialized register reads; (6) every named crypto / protocol spec primitive verified against defining behavior; (7) every unnamed-function behavioral claim checked against its string/dispatch evidence; (8) every "field set to N" checked against an actual store at that offset; (9) check that commit headlines and milestone percentages do not overstate what is decompiled in the wave.
   - **Cover the *current* wave, not only the previous one.** The session-28 final wave shipped with no QA pass and carries two of the nine errors (`tasn_utl`, `obj`). Never let the last wave go unverified — if a run ends on a decompile wave, its QA is still owed.

None of this is a reason to distrust the pipeline: the fabrication-class risks that would make the output unusable are simply absent, and the string-anchored core is excellent. These are the specific guardrails that convert a solid-but-imprecise pass into recompile-grade documentation.

## What's been mapped (the big picture)

- **ITCM/HAL blob** — fully resolved (all 142 distinct thunk targets). FreeRTOS core, a runtime FlexSPI/QSPI flash driver, and a surprising on-device microphone/audio DSP pipeline (FFT, IIR/CIC filters) shared with the `gotham` Wi-Fi firmware. `analysis/bruce-itcm.md`.
- **Broadcom BTA/BTE Bluetooth stack** — located and identified with very high confidence (spec-exact HCI opcodes, event-code tables, SDP/GAP framing). HCI, BTM, GATT client+server, SDP, SMP/pairing, L2CAP, and a resolved AES subsystem (S-box verified byte-for-byte against the raw flash) alongside NIST P-256 ECDH used by SMP's LE Secure Connections pairing. This is the single biggest subsystem in the image (1,076 functions / 204KB) and is 72.9% decompiled but has been untouched for the last several waves — **resuming this sweep is probably the single highest-leverage next action** (see "Suggested next targets" below). `analysis/bruce-bta-stack.md`.
- **BoringSSL crypto stack** — SHA-512, Curve25519/Ed25519, generic ASN.1 (`tasn_dec.c`/`tasn_new.c`), EC/BIGNUM (`bcm.c` — see naming trap below), PEM armor, X9.62 EC codec. `analysis/bruce-crypto.md`.
- **Core gamepad input path** — traced essentially end-to-end: `InputTask` polls 17 GPIO pins on a timer (confirmed debounced, active-low), samples calibrated ADC axes in the same pass, bit-packs everything into a ring buffer. **One hop remains unresolved**: what reads that ring buffer and triggers the final HID transmit call. Four independent sessions each hit a dead end or an invisible-indirect-call wall trying to trace this headlessly — the honest, evidence-backed conclusion is that this specific hop needs **interactive Ghidra GUI work with manual C++ struct/vtable typing**, not more headless attempts. Don't re-litigate this without a genuinely new angle. `analysis/bruce-io-paths.md`.
- **A codebase-wide diagnostic logging framework** — likely the actual mechanism generating the `__FILE__` string leaks this whole project's attribution technique has depended on since day one. Its RPC-triggered dump path (`StreamLogBuffer`) is traced to a generic vtable-based transport; exactly which physical transport (UART/USB-CDC/BLE) it's wired to at runtime is still open. `analysis/bruce-log-buffer.md`.
- **A generic hierarchical state-machine (statechart) framework**, with three confirmed concrete instantiations found so far: BLE adapter pairing/advertising lifecycle, top-level application boot/lifecycle, and headphone volume-control. Genuine LCA-based transition algorithm, run-to-completion dispatch with reentrancy guarding — independently verified, holds up well. `analysis/bruce-state-machine.md`.
- **A full USB Audio Class (host-mode) driver + "Synapse" AEC/AGC/NS voice pipeline** — probably shared-platform code from the same product family as the already-known USB-host gamepad drivers, likely **not actually active** on this BT-only controller SKU (no confirmed live caller into its entry point, though one dispatch function was found wired into a real pointer table — inconclusive either way). Confirmed to be a *separate* DSP stack from the ITCM FFT/IIR pipeline (zero call-graph overlap). `analysis/bruce-audio-subsystem.md`.
- **OTA update mechanism** — an in-band RPC handler streams a new firmware image into the inactive A/B flash partition, CRC-checks it, verifies a build-metadata footer, switches boot slot, and forces a reset. `analysis/bruce-misc-functions.md`.
- **Device identity/provisioning** — loads the BT MAC, decodes BD_ADDR, and fetches/renews a persisted signed device certificate via an internal RPC client (`gotham.cc`) that — despite an earlier session's claim otherwise — **is** confirmed reachable via an unconditional call chain from `main()` at every boot.
- **~67 of 139 attributed source files** are fully decompiled — drivers for the BQ25601 charger, BQ2742x fuel gauge, LP5562 RGB LED, TUSB320 USB-C controller, WM8904 codec (via SAI/I2S), a Cortex-M7 MPU/cache bring-up routine, and more. See `analysis/bruce-decompile-status.md` §2 for the complete list and what's left.

## Known naming traps (don't rediscover these)

- **`keys.cc`** is a generic typed config/property key-value store — not gamepad button state, despite the tempting name.
- **`bcm.c`** is BoringSSL's `crypto/fipsmodule/bcm.c` ("BoringCrypto Module" FIPS aggregate file) — BIGNUM + generic EC code — **not** a Broadcom BT chip driver, despite the name. The real Broadcom HCI transport layer lives in the BTA/BTE block, documented in `bruce-bta-stack.md`.
