# Bruce — the USB-host audio subsystem (`usb_host_audio*.cc`, `usb_audio_receive.cc`, `audio_states.cc`) (session 18)

31 functions across 4 attributed source files, fully decompiled this session (all 4 files now 100% complete — see `bruce-decompile-status.md` §2/§3a). This is a coherent, previously-undocumented subsystem: `bruce` statically links a full **USB-host-mode USB Audio Class (UAC1/UAC2) driver**, layered under a higher-level policy module (`audio_states.cc`) that wires a USB audio device's mic/speaker endpoints into the "Synapse" AEC/AGC/NS voice-processing pipeline. **Correction (session 19 review):** the claim that this pipeline's "low-level FFT/IIR DSP primitives were already mapped in `bruce-itcm.md`" is overstated as written — no shared function call or shared RAM structure was found linking `audio_states.cc`/`synapse_audio_processor.cc` to the FFT/IIR/Ooura-FFT thunk cluster in `bruce-itcm.md` (grepped every address in that cluster against the decompiled files here: zero hits). The two are plausibly related (both are audio-processing-shaped, and `synapse_audio_processor.cc` itself was never decompiled) but this is proximity/plausibility, not a confirmed tie — see the corrected cross-reference note below.

## Why this is here at all

`bruce` is the BT-only firmware for the physical Stadia hand controller, which has no full-size USB-A host port — so a *USB-host* audio-class driver has no obvious on-controller consumer. `firmware-map.md` already flagged the sibling case: `bruce` and `gotham` (the Wi-Fi/WebRTC streaming firmware) share a base-platform SDK that includes "USB host stack with gamepad drivers (DualShock 3 / Switch Pro / Valve Steam Controller)" — i.e. code written for a different physical product (most plausibly a Chromecast-style streaming box that needs to host third-party USB peripherals) that got linked into `bruce` wholesale because both firmwares build from the same platform tree. This session's finding is the audio equivalent of that: a full UAC host driver plus a voice-processing policy layer, almost certainly dead code on the actual controller hardware but real, complete, shippable code in the image. Treat as **shared-platform code, not confirmed-active on this SKU** unless/until a caller into `audio_states__60075088` (the entry point below) is found from a code path known to run on the controller.

## Module map

### `usb_host_audio_topology.cc` (8/8 functions, 2876 bytes) — USB Audio Class descriptor topology parser

Parses the class-specific AudioControl (AC) interface descriptor block (Terminal/Unit descriptors per USB Audio Class 1.0/2.0 §4.3) into an in-memory `std::map`-shaped binary tree keyed by unit/terminal ID, then supports graph traversal over it (e.g. walking from an Output Terminal back through Mixer/Selector/Feature/Processing Units to the matching Input Terminal).

| Function | Size | Role |
|---|---:|---|
| `usb_host_audio_topology__60063cf4` | 212B | Decodes one raw AC-interface descriptor header into an internal node struct: a switch on descriptor subtype (`bDescriptorSubtype`, values 1–0x12) computes each subtype's expected minimum `bLength` (12 for Input Terminal/Mixer-shaped types, 0x11 for a 17-byte type, 9/6/10/8/7 for others, variable-length for Selector/Feature/Extension-Unit-shaped types that carry a trailing pin/channel-count byte) — i.e. a hand-written validator/sizeof table for every USB Audio Class terminal/unit descriptor subtype, confirming `iVar3`/`bDescriptorSubtype` values line up with the spec's `INPUT_TERMINAL`/`OUTPUT_TERMINAL`/`MIXER_UNIT`/`SELECTOR_UNIT`/`FEATURE_UNIT`/... enum. |
| `usb_host_audio_topology__60063e24` | 596B | **Topology builder.** Walks the raw AC-interface descriptor byte stream looking for `'$'`-tagged (0x24, `CS_INTERFACE`) chunks matching a unit-type filter, constructs a 0x34-byte tree node per match (via the 212B decoder above), and inserts it into the binary-tree topology map with a textbook Ghidra-recovered `std::map` red-black insert (`thunk_FUN_60101ccc`/`thunk_EXT_FUN_0000b52a` rotate/rebalance helpers). This is where the map consumed by every other function in this file gets built. |
| `usb_host_audio_topology__6006408c` / `600641a8` / `60064438` / `60064110` | 120B/622B/156B/142B | Map lookup, ID-chain parsing, recursive graph DFS (cycle-detected via a per-node "visited" byte), and a two-bucket node-list builder (tags nodes 0x100 vs 0x200 by a predicate) respectively — the traversal primitives used by the state machine below to resolve "which Feature Unit controls this Terminal" and "what's the active Clock Source". |
| `usb_host_audio_topology__60063c08` | 72B | Descriptor-length sanity `CHECK`. |
| `usb_host_audio_topology__600644dc` | 956B | **The big one — format/route resolver.** Given target sample-rate/channel/format criteria, walks a Terminal's connected AudioStreaming interface's alternate settings to find one whose Type-I/Type-II format descriptor matches, returning the winning altsetting index plus a sample-rate-range struct. Branches on `*(param_1+0x79)` (the AC interface's protocol byte) with two completely different code paths: `0x00` and `' '` (**0x20**) — these are exactly the real USB Audio Class `bInterfaceProtocol` values `IP_VERSION_01_00` (UAC1) and `IP_VERSION_02_00` (UAC2), confirming this driver supports both AC spec generations with genuinely different (fixed-endpoint-rate vs Clock-Source-object) format-negotiation logic. |

### `usb_host_audio.cc` (9/9 functions, 2346 bytes) — the UAC host driver's state machine

`usb_host_audio__6006318c` (1176 bytes) is a 17-state (`switch` cases 0–0x10) driver state machine, each transition posted via `usb_host_worker__600d56ae(obj, next_state)` (an already-attributed but not-yet-decompiled sibling file — the generic USB-host per-device worker/event-queue, out of scope this session). Inferred per-state roles (medium confidence — inferred from call targets + literal log strings, not cross-checked against a spec doc):

| State | Role |
|---:|---|
| 0 | Idle/no-op guard; cancels a stale pending I/O if re-entered. |
| 1 | Enumerate the device's interfaces looking for a usable AudioStreaming alternate setting (endpoint-count threshold check). |
| 2 | Find + claim the AudioControl (AC) interface by class/subclass; on success frees any stale topology and calls the topology builder (`usb_host_audio_topology__60064110`). Logs `"Unable to find control interface #%d"` / `"Unable to set control interface"` on failure. |
| 3 | GET_CUR the active Clock Source ID (UAC2 path) — `"Failed to query clock source #%d"` on error. |
| 4 | Resolve the Feature Unit IDs for each logical path (mic/speaker/sidetone, stored at `+0x35`/`+0x99`/`+0xfd`) via `usb_host_audio_topology__600644dc`, then SET_CUR the sampling frequency. `"Unable to find streaming interface(s)"` / `"Error setting interface units"` on failure. |
| 5 | Endpoint bandwidth/rate configuration — logs `"USB <speaker\|mic> will <play\|record> at <rate>kHz, <bits>-bit, <ch>ch"`; UAC1 path SET_CURs a fixed sampling-frequency endpoint request, UAC2 path SET_CURs the Clock Source/Clock Selector object instead. |
| 6 | Protocol-version gate: `0x00`(UAC1)/`0x20`(UAC2) proceed, anything else is an error. |
| 7, 8 | Feature-Unit GET/SET_CUR requests (mute / a second control) against the resolved Feature Unit ID at `+0x108`. |
| 9–12 | Select the active logical path (Speaker=0x82/Mic=0x83/Sidetone=0x84/Default=0x81, per `usb_host_audio__60062b1c`'s own switch) for the next Feature-Unit request. |
| 13 | Query + log the volume-control range (min/max/res/cur) for the active path's Feature Unit — via `usb_host_audio__60062aa8`/`60062a10`/`60062a74`, which log `"Mute change supported: %s"` / `"Volume change supported: %s"` / `"Min: %d Max: %d Res: %d Cur: %d"`. |
| 14 | Kick off isochronous IN (mic) and OUT (speaker) transfers for both directions via `usb_host_audio__60062f9c`. |
| 15, 16 | Terminal error states — `"Entering ERROR state"` / `"Entering invalid state"`. |

`usb_host_audio__60062f9c` (450B) is the isochronous transfer-completion handler shared by both directions: on each completed USB frame it advances a ring-buffer write cursor, detects overflow (notifies a waiting task via a semaphore-like primitive), and re-submits the next transfer (`usb_host_audio__60062ba4`/`60062c70`, mic-in vs speaker-out request builders, 178B/160B).

### `usb_audio_receive.cc` (8/8 functions, 1994 bytes) — the mic-in receive worker task

`usb_audio_receive__6007a62c` (772B, self-identifies via the log string `"Usb audio receiving thread is pr[oceeding]..."`) is a **FreeRTOS task loop**: waits on a task notification with an adaptive timeout (computed from a running buffer-fill estimate, `usb_audio_receive__60079f1c`'s underrun threshold logic), then on wake copies newly-arrived isochronous frames out of the double-buffered capture ring (`FUN_600dbbd0`) and, once enough data has accumulated, forwards a frame to the recording pipeline via a vtable call (`(**(code**)(*piVar6+8))()` — a generic "audio sink" interface, consistent with the intrusive-refcounted-object pattern documented in `bruce-itcm.md`). Uses the same `DataMemoryBarrier`/`ExclusiveAccess`/`hasExclusiveAccess` (LDREX/STREX) atomic-flag idiom seen in `bruce-itcm.md`'s atomic-refcount thunk, here guarding several single-byte "event pending" flags shared with the ISR/transfer-completion side.

`usb_audio_receive__6007a040`/`6007a504`/`6007a118` implement **sample-rate feedback / drift correction**: `6007a040` computes a 3-way rate-correction code (`+1`/`-1`/none) by comparing the buffer fill level against `0x180`/`0x900`/`0xcc0`-byte thresholds and pushes it out via `usb_device_audio__60061fc0` — this is the classic USB Audio Class 1.0 **feedback endpoint** (10.14 fixed-point rate value) mechanism for adjusting the source's isochronous rate to match the local clock. `6007a504` is the underrun/overrun-repair path (logs `"Not enough room in buffer to fill... ms audio gap"` / `"USB Audio discontinuity linear i[nterp]"`) that linearly interpolates across a detected gap. `6007a998` is the receiver object's lazy singleton constructor/refcount-acquire (first caller allocates + starts the task above; subsequent callers atomically bump a refcount via the same LDREX/STREX pattern).

### `audio_states.cc` (6/6 functions, 2392 bytes) — voice-path policy / AEC-backend selection

The policy layer that decides *how* to process mic/speaker audio and wires the USB-host-audio objects above into it.

- **`audio_states__60075088`** (1892B, by far the largest of the four files) — the entry point: creates a USB audio source (`usb_audio_receive__6007a998`) and sink (`usb_audio_send__6007ad34`, sibling file not decompiled this session), then reads a cluster of config keys via the generic typed KV store (`keys__60066370`, key IDs `0xf`–`0x13`, confirmed-attributed in `key_value_store.cc`/`keys.cc`) to pick an **echo-cancellation backend**: forced-off, `"Synapse"` (a named internal AEC/AGC/NS library — distinct from the literal-confirmed WebRTC/Ooura-FFT DSP chain in `bruce-itcm.md`, though it plausibly sits on top of the same primitives), with named AEC/NS/AGC sub-modes (`"SettingsDefault"` and others) and a processing sample rate (16 kHz default vs 48 kHz, delegated to `audio_states__60074c2c`). Constructs a `synapse_audio_processor` object (`synapse_audio_processor.cc`, sibling file, not decompiled this session) wired to the source/sink pair, then starts the capture (`recording_pipeline__6007ed74`/`6007edf4`) and playback (`audio_tasks__60079d28`) pipelines. On any failure it logs `"Audio setup failed to set the pl[ayback path]"` / `"Failed to setup audio paths and a[ctions]"` and unwinds. Confirms the literal chain `"Setting up usb audio source"` → `"Using 'Synapse' AEC"` / `"No AEC setting forced. Using... Synapse"` → `"Unknown echo cancellation type: %s"` seen directly in the decompiled strings.
- **`audio_states__60074c2c`** (124B) — reads config key `0x13`/type `7`, matches literal strings `"default"`/`"16000"`/`"48000"`, returns the internal-processing-rate flag (defaults to 16 kHz, logs which rate was chosen and why).
- **`audio_states__60074e6c`/`60074d54`/`60074dfc`/`60074f70`** (80B/44B/56B/196B) — small ctor/on-enter/on-exit-shaped handlers (one constructs a refcounted wrapper object with an explicit vtable pointer, `PTR_PTR_60075034`; two others are trivial "if channel present, do X else log" pairs). Shape strongly suggests these are concrete state-callback instantiations of the generic hierarchical-state-machine framework documented in `bruce-state-machine.md` (on-enter/on-exit dispatch), though no direct caller into the base-class dispatcher was traced this session — flagged as a loose end below rather than asserted.

## Session 20: `synapse_audio_processor.cc` — the Synapse AEC/AGC/NS object itself (2/2 decompiled)

`synapse_audio_processor.cc` was `bruce-decompile-status.md`'s #4 cheap-win target (1,060 remaining bytes, 0/2) and the exact file session 19's review flagged as "the one file that could actually make this connection concrete." Both attributed functions are now decompiled (`analysis/decomp/synapse_audio_processor__*.c`), which **settles the open question from the correction below: no link to `bruce-itcm.md`'s FFT/IIR/CIC cluster.** Every callee address in both functions (`FUN_600dc38e`, `FUN_600dc30e`, `FUN_601017fc`/`601017e8`/`6010177a`, `thunk_EXT_FUN_0000b532`/`0000b52e` (malloc/free), `thunk_EXT_FUN_00001680`, `FUN_6007aeb0`, `FUN_600dbf20`, `thunk_EXT_FUN_000078b0`, `FUN_600d5252`, `FUN_600cc984`/`600cc8f8`, `FUN_600d53ae`, `thunk_EXT_FUN_00002dec`, `FUN_600d3b3a`/`600d37ac`) was checked against every thunk address `bruce-itcm.md` catalogs in the `0x60043xxx`–`0x6004bxxx` FFT/IIR/Ooura-FFT range — **zero overlap.**

- **`synapse_audio_processor__6007b1b8`** (928B) — **the constructor.** Builds a large (~24 KB, `0x5f18`-byte) opaque state object via a single call to `FUN_600dc38e(state, config, sampleRateHz)` — a black-box call into what's almost certainly the actual vendored "Synapse" AEC/AGC/NS library (its internals are not visible here; this file only ever *allocates and configures* it, never processes samples directly). Before that call it builds one of three fixed parameter-preset structs (selected by `param_5` — modes `0`/`1`/`2`, matching `audio_states.cc`'s `"SettingsDefault"`-style named sub-modes) containing what look like AEC filter-length/delay/gain float constants (`0x40800000` = 4.0f appears repeatedly). After construction, wraps the Synapse state plus the source/sink pair into a second ~0x10-word task-control object and starts a dedicated FreeRTOS task (`FUN_6010177a(..., "SynapseAEC_Task", priority=6)`) — confirming "Synapse" runs as its **own RTOS task**, separate from the USB-host-audio driver's task(s).
- **`synapse_audio_processor__6007b600`** (132B) — **the task body**, i.e. what `SynapseAEC_Task` actually runs: a loop that waits on a task-notification (`thunk_EXT_FUN_000078b0`, FreeRTOS `ulTaskNotifyTake`-shaped), checks/clears a "channel changed" event flag, waits up to 60 seconds on an event-group-shaped primitive (`FUN_600d5252`) logging `"..."` (string not resolved from this decompile alone) on timeout, then calls a per-iteration processing step (`thunk_EXT_FUN_00002dec`) in an inner retry loop until it returns 0. This is the task's outer scheduling loop, not the DSP math itself — the actual sample processing is presumably inside `thunk_EXT_FUN_00002dec` or further inside the opaque Synapse state object neither of these two functions expose.

**Net, replacing the speculative correction below**: `synapse_audio_processor.cc` is a **thin RTOS-task wrapper around a large, opaque, vendored "Synapse" AEC/AGC/NS library object** — it allocates ~24 KB for that library's internal state, configures it from one of 3 fixed presets, and runs it on its own dedicated task, but performs no FFT/IIR/CIC math itself. **This firmware image therefore contains two structurally distinct, non-overlapping audio-DSP stacks**: (1) the hand-written, WebRTC/Ooura-FFT-shaped pipeline mapped in `bruce-itcm.md` (mic capture → FFT → Wiener-gain NS → CIC decimation), and (2) this opaque "Synapse" library that `audio_states.cc` selects as an alternative/additional AEC backend for the USB-host-audio path. Nothing found this session ties the two together — they remain two separate subsystems, not layers of one pipeline as earlier prose speculated.

## Session 21: `usb_device_audio.cc` (3/3 decompiled) — the feedback-endpoint transport `usb_audio_receive.cc` calls into

`usb_device_audio.cc` was `bruce-decompile-status.md`'s §3a cheap-win target (540 remaining bytes, 0/3), and exactly the file the "Not chased this session" note above flagged as `usb_audio_receive__6007a040`'s feedback-endpoint transport. All 3 attributed functions are now decompiled (`analysis/decomp/usb_device_audio__*.c`).

- **`usb_device_audio__60061fc0`** (222B) — **sends the USB Audio Class 1.0 feedback-endpoint sample-rate-correction value**, called directly from `usb_audio_receive__6007a040` (session 18, above). Under the same LDREX/STREX-guarded "in-flight" flag idiom this codebase uses elsewhere, stashes the 4-byte 10.14-fixed-point rate value and issues the transfer (`FUN_600d0602(handle, 5, buf, 4)` — endpoint/pipe `5`); on failure, waits up to 5 seconds for the pipe to recover before giving up and logging `"Failed to send USB audio feedbac[k]..."` with the numeric error code.
- **`usb_device_audio__60061ed4`** (216B) — **sends actual audio sample data** (up to `0x60`/96 bytes per call, clamped) over pipe `6` via the same "copy into a scratch buffer, issue transfer, retry-wait-on-failure" shape as the function above — the USB-device-mode **speaker/playback OUT** path (as opposed to `usb_device_audio__60061fc0`'s feedback-only 4-byte packets).
- **`usb_device_audio__600620b4`** (102B) — small **teardown/cancel** helper: cancels any pending transfer on pipe `5` (`FUN_600d5240`) and, if one was actually in flight, logs the numeric cancel-status code.

**Net:** confirms and closes out the open thread from session 18 — `usb_audio_receive.cc`'s rate-feedback logic (fill-level → `+1`/`-1`/none correction code) and `usb_device_audio.cc`'s transport (this file) are a matched pair implementing the standard **USB Audio Class 1.0 explicit feedback endpoint** mechanism end to end, on the USB **device**-mode side (i.e. this is the Stadia controller acting as a USB audio device when plugged into a host over the wired USB-C port — distinct from the USB-**host**-mode UAC driver `usb_host_audio.cc` documents for the reverse scenario of something else being plugged into the controller). `usb_device_audio__60061ed4`'s speaker-data path suggests device-mode USB audio *playback* (e.g. wired headset audio routed through the controller from a host) is also supported, not just mic capture.

## Session 21: `headphone_state_machine.cc` (5/5 decompiled) — the `HeadphoneStateMachine` object and volume-control path

`headphone_state_machine.cc` was `bruce-decompile-status.md`'s §3a cheap-win target (672 remaining bytes, 0/5). All 5 attributed functions are now decompiled (`analysis/decomp/headphone_state_machine__*.c`). This is a small, self-contained **audio-output routing/volume-control state object** — genuinely new territory, distinct from both the USB-host-audio cluster above and the mic-capture DSP pipeline (`bruce-itcm.md`).

- **`headphone_state_machine__60075b18`** (194B) — **the constructor**, `HeadphoneStateMachine(self, channel)`. Builds a fixed 21-byte identifier string (via a manual byte-copy loop off a literal `PTR_s_HeadphoneStateMachine_...`, i.e. the class's own name is baked in as a debug-ID string), initializes a base-class sub-object (`FUN_60083fd0`, vtable-shaped), wires up several vtable/constant pointers, and initializes an embedded list/queue-shaped field (`FUN_601017e8`). Logs a `CHECK failed` assertion (referencing the shared `"CHECK failed"` idiom `bruce-itcm.md`/`bruce-log-buffer.md` document elsewhere) if constructed with a null channel argument.
- **`headphone_state_machine__60075c50`** (270B) — **the volume-set entry point.** Queries the current min/max volume range from a channel object's vtable (offset `+0x14`), computes a target dB value by linearly interpolating between them using a `param_1` fraction (`0.0`–`1.0`), and applies it via another vtable call (offset `+0x18`) — logs `"Failed to set sound codec volume to..."` with the computed dB value on failure, or `"Failed to get sound codec volume"` if the initial range query itself failed. The `param_2+0x78` vtable-object pointer this and the next function dereference is a generic "audio output channel" interface, not specific to any one codec.
- **`headphone_state_machine__60075d78`** (152B) — **a second, USB-specific volume-set path**, converting a float `0.0`–`1.0` fraction to a fixed-point USB Audio Class volume code (`VectorFloatToUnsigned`) and setting it via a different vtable slot (offset `+0x1c`) on the same channel object — logs `"Failed to set USB volume to <n> with error <code>"` on failure. Two distinct volume-set paths on the same object strongly suggests this state machine drives **both** a local sound codec (matching the attributed-but-undecompiled `sound_codec_wm8904.cc` sibling — the WM8904 codec — via `60075c50`) **and** a USB Audio Class device's Feature Unit volume control (via `60075d78`, likely the `usb_host_audio.cc` Feature-Unit GET/SET_CUR calls `bruce-audio-subsystem.md`'s session-18 write-up documents) from one unified interface — i.e. this is the policy layer that lets "set headphone volume" work identically whether the sound is coming out through the onboard WM8904 codec or through an attached USB audio accessory.
- **`headphone_state_machine__60075c08`** / **`60075c2c`** (28B each) — a matched pair of thin log-and-forward shims: each logs a fixed trace line then makes an indirect vtable call (offsets `+8` and `+0xc` respectively off a nested object) — shape-consistent with **on-enter**/**on-exit** state-transition hooks in the same hierarchical-state-machine framework `bruce-state-machine.md` documents (the class's own name, `HeadphoneStateMachine`, plus this on-enter/on-exit shape, makes it near-certain this is a concrete instantiation of that generic HSM engine, in the same family as `audio_states.cc`'s state-callback handlers noted above).

**Net:** `HeadphoneStateMachine` is a hierarchical-state-machine-framework object (per `bruce-state-machine.md`'s engine) that unifies volume control across the onboard WM8904 sound codec and an attached USB audio accessory's Feature Unit — plausibly the policy that decides "where is headphone audio actually going right now" and keeps volume settings consistent across that transition (e.g. plugging in a USB headset vs. using the built-in 3.5mm jack via the WM8904). No caller into the constructor was found this session; `sound_codec_wm8904.cc` (2 functions, still undecompiled) is the natural next hop to fully resolve the onboard-codec half of this picture.
