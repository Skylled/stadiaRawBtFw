# Bruce — `state_machine.cc`: the generic hierarchical-state-machine framework (session 17)

Decompiled C for every function cited here is in `analysis/decomp/state_machine__*.c`. Picked up as one of `bruce-decompile-status.md`'s §3a cheap-win files (2,728 remaining bytes, 1/11 done); all 10 remaining functions decompiled this session, giving 11/11 formally-attributed functions plus the already-decompiled `state_machine__600df264` (604B) that had been carved out earlier. This is genuinely new territory — it doesn't fit the FreeRTOS/ITCM story (`bruce-itcm.md`), the crypto stack (`bruce-crypto.md`), or the BTA/BTE stack (`bruce-bta-stack.md`) directly, though it *drives* pieces of the last one.

## What it is

`state_machine.cc` is a small **generic C++ hierarchical state machine (statechart) base class**, instantiated at least once in this firmware to drive the BLE adapter's pairing/advertising mode. It's built directly on top of the codebase-wide diagnostic `Buffer` logging framework (`bruce-log-buffer.md` — `FUN_600d37ac`/`FUN_600d3b3a`/`FUN_600d3b24`/`FUN_600dff54`/`FUN_600dff76`/`FUN_60101740`/`FUN_601016f0` all appear verbatim as the "format and emit a debug trace" calls guarding almost every function here) and the `std::optional<T>`-shaped `{value, bool}` tagged-union helpers already identified in `bruce-itcm.md` (`thunk_EXT_FUN_0000ab28`/`0xab36`/`0xab42` = copy-if-valid / guard-and-trap / prefer-valid merge, `FUN_6004b344`/`FUN_6004b352`/`FUN_6004b35e`).

**Correction (independent verification pass):** `FUN_600dff98`, despite sharing an address neighborhood with the true trace formatters `FUN_600dff54`/`FUN_600dff76`, is **not** one of them — every call site (`600842ac`, `600841d0`, `600843c8`, `60084644`) sits *outside* the `param_1+0x5a`/`0x5b` debug-flag-gated blocks and is part of the real algorithm: it's the `(dest, this, src)`-shaped accessor used to fetch a state's parent in the ancestor-chain walk (`600842ac`) and to re-derive the pending-event field after on-exit (`600841d0`). The per-function table below already described it correctly in those two rows; only this summary paragraph had mis-bucketed it as a logging call.

Two identifiable layers:

### 1. The generic HSM engine (state-agnostic)

| Function | Size | Role |
|---|---:|---|
| `state_machine__60084644` | 594B | **The run-to-completion event-dispatch loop.** Dequeues a pending event (the `std::optional`-shaped queue-slot accessor), calls the current state's virtual "handle event" method (vtable slot `+0x1c`) which returns an `{next_state, handled, terminate}`-shaped optional result, loops if unhandled, and — once a transition is decided — invokes `state_machine__600843c8` (below) to actually perform it. Logs entry/exit traces if a debug flag (`param_1+0x5b`) is set. |
| `state_machine__600843c8` | 594B | **The transition executor (least-common-ancestor algorithm).** Walks the ancestor chain of both the *from* and *to* states via `state_machine__600842ac` (below, called twice, once per side, max depth 16), finds where the two chains first diverge (the LCA), calls `state_machine__600841d0` ("on-exit", below) in a loop to exit every state from *from* up to (not including) the LCA, then calls `state_machine__60084104` ("on-enter", below) for every state from the LCA down to *to*. This is the textbook UML-statechart transition algorithm (exit-to-LCA, enter-from-LCA) — strong, structurally-unambiguous evidence this is a real hierarchical (not flat) state machine, not just a switch-table FSM. |
| `state_machine__600842ac` | 256B | Fixed-size (max 16-deep, `0x10`) ancestor-chain collector / small ring-buffer append helper — pushes state IDs into a caller-supplied array via the vtable's "get parent" accessor, reversing the result so index 0 = the state itself and the end = the root. Used by the transition executor to build both sides' ancestor chains before finding the LCA. |
| `state_machine__60084104` | 176B | **"on-enter"**: merges the new pending-event value into the state's stored current-event field (optional "prefer existing" merge), then calls the virtual "on enter" method (vtable `+0x20`). Logs a debug trace first if enabled. |
| `state_machine__600841d0` | 190B | **"on-exit"**: reads the state's stored pending-event value (assert-if-empty), calls the virtual "on exit" method (vtable `+0x24`), then re-derives and re-merges the current-event field. Always executes (no debug-flag guard around the call itself, only around the trace). |
| `state_machine__600848bc` | 204B | **One-time lazy-init gate**: on first call (guarded by `param_1+0x59`), queries the initial-state descriptor twice (a dedup/confirm pattern) and calls two external hooks (`FUN_600e002e`, `FUN_600e008a` — not part of this file) to kick off processing of the initial state. |
| `state_machine__600849a4` | 266B | **The public "post event" entry point.** Ensures init (`600848bc`), then: if the machine isn't already mid-dispatch (reentrancy guard at `param_1+0x58`), runs the dispatch loop (`60084644`) synchronously; if it *is* mid-dispatch (an event posted from inside a state's own handler), queues the new event into a small fixed-capacity ring buffer instead of recursing (falling back to an external overflow handler `FUN_600e00ca` if the ring is full) — the classic **run-to-completion reentrancy guard** every statechart implementation needs so a state handler can safely post further events without re-entering the dispatcher. |

The virtual-dispatch offsets recovered so far: `vtable+0x1c` = handle-event, `vtable+0x20` = on-enter, `vtable+0x24` = on-exit. Concrete state subclasses (individual `onEnter`/`onExit`/`handleEvent` overrides) were not chased this session — the vtable calls are all `(**(code**)(*param_1 + offset))(...)`, genuine indirect dispatch through an untyped object, same style as the `adapter.cc`/GATT-callback dead ends `bruce-io-paths.md` sessions 10-16 already ran into. Not attempted here; flagged as a possible follow-up if anyone wants concrete per-state behavior rather than the engine shape.

### 2. A concrete instantiation: the BLE adapter pairing/advertising-mode state machine

| Function | Size | Role |
|---|---:|---|
| `state_machine__6008099c` | 200B | **OOBE (out-of-box-experience) event gate.** Special-cases event id `7` (marks a "seen at least once" flag persistently at `param_1+0xe4`); if that flag isn't set yet, discards the event with a `"Discarding OOBE event ... (seen before startup)"` trace; otherwise computes the target state via `state_machine__600805e4` (the transition table, below) and, if it actually changes anything, drives the real transition via `state_machine__600df264` and logs `"Transitioned to <state> after <event>"`. Only caller found is `application_state__6005b8dc` (one of the top-10 cheap-win files itself, still undecompiled — a natural next hop for whoever picks that file up). |
| `state_machine__600805e4` | 110B | **The event → next-state transition table**, encoded as a `switch` on an 8-value event id (0–7) producing a 7-value state id (0–6), with a couple of states short-circuiting through `FUN_600df218()` (current-adapter-state getter) to decide between two possible outcomes and an `assert`-then-recover default for unrecognized event ids. This is literally the FSM's edge table for whatever high-level mode the BLE adapter is in; exact state/event names weren't recoverable from this session's evidence (no string table nearby), but the shape (~7 states, transitions gated on "are we currently connected/discoverable") is consistent with a **BT pairing-mode / discoverability state machine** — Off, Connectable, LimitedDiscoverable, GeneralDiscoverable, Connected, and 1-2 transitional states would be a plausible real-world fit, unconfirmed. |
| `state_machine__60080390` | 138B | **State → descriptor classifier.** Converts a raw state id (1–5, plus 0 and other defaults) into a packed 3-field descriptor (two bool-shaped flags + a small struct), logging a warning (`FUN_60101740`) on a specific invalid-looking combination. Used by `600df264` to compare the *old* and *new* states' descriptors rather than the raw ids, presumably to answer "does this transition actually change discoverability/connectability" rather than "did the numeric id change." |
| `state_machine__600df264` (604B, decompiled prior to this session, now cross-referenced here) | 604B | **The concrete "apply a new adapter state" implementation — ties `adapter.cc`, `advertiser.cc`, and `gatt_manager_task.cc` together.** Computes descriptors for the current and target states via `state_machine__60080390`; if the connectable/pairable-shaped flag differs between them: tears the GATT server down (stop advertising, decrement a refcounted GATT-manager-task handle, and if it drops to zero, log `"Gatt Manager shutting down"` and release it) when going from active→inactive, or spins the GATT manager task up (`gatt_manager_task__60080cdc`, logging `"BLE services setup"`) when going inactive→active. Either way it then unconditionally re-arms the advertiser with new parameters (`advertiser__60081234`) and, depending on the target state, schedules either a "limited discovery" timeout or a general discoverability-timeout re-check before recording the new state. |

**Why this matters beyond just closing a cheap-win file:** `analysis/bruce-bta-stack.md`'s `adapter.cc` section (session 15) and `analysis/bruce-io-paths.md`'s open thread #1 both work with `adapter.cc`/`gatt_server.cc`/`gatt_manager_task.cc` in isolation. This session found the actual **orchestration layer above all three** — `state_machine__600df264` is concretely the function that decides "should the controller be advertising for pairing right now" and drives the GATT server process lifecycle (start/stop, refcounted) in response. It does **not** close CLAUDE.md's open thread #1 (the report-packing GATT-characteristic-callback invoker is still unresolved — this state machine governs *pairing/discoverability mode*, a different, higher-level concern from "who reads the HID ring buffer once already connected"), but it's a real, previously-undocumented piece of the BLE connection-management picture, and a plausible next place to look if the pairing/bonding flow itself (rather than the post-connection HID path) becomes the priority.
