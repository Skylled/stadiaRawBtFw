# Bruce — `state_machine.cc`: the generic hierarchical-state-machine framework (session 17)

Decompiled C for every function cited here is in `analysis/decomp/state_machine__*.c`. Picked up as one of `bruce-decompile-status.md`'s §3a cheap-win files (2,728 remaining bytes, 1/11 done); all 10 remaining functions decompiled this session, giving 11/11 formally-attributed functions plus the already-decompiled `state_machine__600df264` (604B) that had been carved out earlier. This is genuinely new territory — it doesn't fit the FreeRTOS/ITCM story (`bruce-itcm.md`), the crypto stack (`bruce-crypto.md`), or the BTA/BTE stack (`bruce-bta-stack.md`) directly, though it *drives* pieces of the last one.

## What it is

`state_machine.cc` is a small **generic C++ hierarchical state machine (statechart) base class**, instantiated at least once in this firmware to drive the BLE adapter's pairing/advertising mode. It's built directly on top of the codebase-wide diagnostic `Buffer` logging framework (`bruce-log-buffer.md` — `FUN_600d37ac`/`FUN_600d3b3a`/`FUN_600d3b24`/`FUN_600dff54`/`FUN_600dff76`/`FUN_60101740`/`FUN_601016f0` all appear verbatim as the "format and emit a debug trace" calls guarding almost every function here) and the `std::optional<T>`-shaped `{value, bool}` tagged-union helpers already identified in `bruce-itcm.md` (`thunk_EXT_FUN_0000ab28`/`0xab36`/`0xab42` = copy-if-valid / guard-and-trap / prefer-valid merge, `FUN_6004b344`/`FUN_6004b352`/`FUN_6004b35e`).

**Correction (independent verification pass):** `FUN_600dff98`, despite sharing an address neighborhood with the true trace formatters `FUN_600dff54`/`FUN_600dff76`, is **not** one of them — every call site (`600842ac`, `600841d0`, `600843c8`, `60084644`) sits *outside* the `param_1+0x5a`/`0x5b` debug-flag-gated blocks and is part of the real algorithm: it's the `(dest, this, src)`-shaped accessor used to fetch a state's parent in the ancestor-chain walk (`600842ac`) and to re-derive the pending-event field after on-exit (`600841d0`). The per-function table below already described it correctly in those two rows; only this summary paragraph had mis-bucketed it as a logging call.

Two identifiable layers:

### 1. The generic HSM engine (state-agnostic)

| Function | Size | Role |
|---|---:|---|
| `state_machine__60084644` | 594B | **The run-to-completion event-dispatch loop.** Dequeues a pending event (the `std::optional`-shaped queue-slot accessor), calls the current state's virtual "handle event" method (vtable slot `+0x1c`) which returns an `{next_state, handled, terminate}`-shaped optional result, loops if unhandled, and — once a transition is decided — invokes `state_machine__600843c8` (below) to actually perform it. Logs entry/exit traces if a debug flag (`param_1+0x5b`) is set. |
| `state_machine__600843c8` | 594B | **The transition executor (least-common-ancestor algorithm).** Walks the ancestor chain of both the *from* and *to* states via `state_machine__600842ac` (below, called twice, once per side, max depth 16), finds where the two chains first diverge (the LCA), calls `state_machine__600841d0` ("on-exit", below) in a loop to exit every state from *from* up to (not including) the LCA, then calls `state_machine__60084104` ("on-enter", below) for every state from the LCA down to *to*. This is the textbook UML-statechart transition algorithm (exit-to-LCA, enter-from-LCA) — strong, structurally-unambiguous evidence this is a real hierarchical (not flat) state machine, not just a switch-table FSM. |
| `state_machine__600842ac` | 256B | Fixed-size (max 16-deep, `0x10`) ancestor-chain collector / small ring-buffer append helper — pushes state IDs into a caller-supplied array via the vtable's "get parent" accessor, reversing the result so index 0 = the state itself and the end = the root. Used by the transition executor to build both sides' ancestor chains before finding the LCA. |
| `state_machine__60084104` | 176B | **"on-enter"**: merges the new pending-event value into the state's stored current-event field (optional "prefer existing" merge), then calls the virtual "on enter" method (vtable `+0x20`). Logs a debug trace first if enabled. |
| `state_machine__600841d0` | 190B | **"on-exit"**: reads the state's stored pending-event value (assert-if-empty), calls the virtual "on exit" method (vtable `+0x24`), then re-derives and re-merges the current-event field. Always executes (no debug-flag guard around the call itself, only around the trace). |
| `state_machine__600848bc` | 204B | **One-time lazy-init gate**: on first call (guarded by `param_1+0x59`), queries the initial-state descriptor twice (a dedup/confirm pattern) and calls two external hooks (`FUN_600e002e`, `FUN_600e008a` — not part of this file) to kick off processing of the initial state. |
| `state_machine__600849a4` | 266B | **The public "post event" entry point.** Ensures init (`600848bc`), then: if the machine isn't already mid-dispatch (reentrancy guard at `param_1+0x58`), runs the dispatch loop (`60084644`) synchronously; if it *is* mid-dispatch (an event posted from inside a state's own handler), queues the new event into a small fixed-capacity ring buffer instead of recursing (falling back to an external overflow handler `FUN_600e00ca` if the ring is full) — the classic **run-to-completion reentrancy guard** every statechart implementation needs so a state handler can safely post further events without re-entering the dispatcher. |

The virtual-dispatch offsets recovered so far: `vtable+0x1c` = handle-event, `vtable+0x20` = on-enter, `vtable+0x24` = on-exit. Concrete state subclasses (individual `onEnter`/`onExit`/`handleEvent` overrides) were not chased this session — the vtable calls are all `(**(code**)(*param_1 + offset))(...)`, genuine indirect dispatch through an untyped object, same style as the `adapter.cc`/GATT-callback dead ends `bruce-io-paths.md` sessions 10-16 already ran into. Not attempted here; flagged as a possible follow-up if anyone wants concrete per-state behavior rather than the engine shape.

### 2. A concrete instantiation: the BLE adapter pairing/advertising-mode state machine

| Function | Size | Role |
|---|---:|---|
| `state_machine__6008099c` | 200B | **OOBE (out-of-box-experience) event gate.** Special-cases event id `7` (marks a "seen at least once" flag persistently at `param_1+0xe4`); if that flag isn't set yet, discards the event with a `"Discarding OOBE event ... (seen before startup)"` trace; otherwise computes the target state via `state_machine__600805e4` (the transition table, below) and, if it actually changes anything, drives the real transition via `state_machine__600df264` and logs `"Transitioned to <state> after <event>"`. Only caller found is `application_state__6005b8dc` (one of the top-10 cheap-win files itself, still undecompiled — a natural next hop for whoever picks that file up). |
| `state_machine__600805e4` | 110B | **The event → next-state transition table**, encoded as a `switch` on an 8-value event id (0–7) producing a 7-value state id (0–6), with a couple of states short-circuiting through `FUN_600df218()` (current-adapter-state getter) to decide between two possible outcomes and an `assert`-then-recover default for unrecognized event ids. This is literally the FSM's edge table for whatever high-level mode the BLE adapter is in; exact state/event names weren't recoverable from this session's evidence (no string table nearby), but the shape (~7 states, transitions gated on "are we currently connected/discoverable") is consistent with a **BT pairing-mode / discoverability state machine** — Off, Connectable, LimitedDiscoverable, GeneralDiscoverable, Connected, and 1-2 transitional states would be a plausible real-world fit, unconfirmed. |
| `state_machine__60080390` | 138B | **State → descriptor classifier.** Converts a raw state id (1–5, plus 0 and other defaults) into a packed 3-field descriptor (two bool-shaped flags + a small struct), logging a warning (`FUN_60101740`) on a specific invalid-looking combination. Used by `600df264` to compare the *old* and *new* states' descriptors rather than the raw ids, presumably to answer "does this transition actually change discoverability/connectability" rather than "did the numeric id change." |
| `state_machine__600df264` (604B, decompiled prior to this session, now cross-referenced here) | 604B | **The concrete "apply a new adapter state" implementation — ties `adapter.cc`, `advertiser.cc`, and `gatt_manager_task.cc` together.** Computes descriptors for the current and target states via `state_machine__60080390`; if the connectable/pairable-shaped flag differs between them: tears the GATT server down (stop advertising, decrement a refcounted GATT-manager-task handle, and if it drops to zero, log `"Gatt Manager shutting down"` and release it) when going from active→inactive, or spins the GATT manager task up (`gatt_manager_task__60080cdc`, logging `"BLE services setup"`) when going inactive→active. Either way it then unconditionally re-arms the advertiser with new parameters (`advertiser__60081234`) and, depending on the target state, schedules either a "limited discovery" timeout or a general discoverability-timeout re-check before recording the new state. |

**Why this matters beyond just closing a cheap-win file:** `analysis/bruce-bta-stack.md`'s `adapter.cc` section (session 15) and `analysis/bruce-io-paths.md`'s open thread #1 both work with `adapter.cc`/`gatt_server.cc`/`gatt_manager_task.cc` in isolation. This session found the actual **orchestration layer above all three** — `state_machine__600df264` is concretely the function that decides "should the controller be advertising for pairing right now" and drives the GATT server process lifecycle (start/stop, refcounted) in response. It does **not** close CLAUDE.md's open thread #1 (the report-packing GATT-characteristic-callback invoker is still unresolved — this state machine governs *pairing/discoverability mode*, a different, higher-level concern from "who reads the HID ring buffer once already connected"), but it's a real, previously-undocumented piece of the BLE connection-management picture, and a plausible next place to look if the pairing/bonding flow itself (rather than the post-connection HID path) becomes the priority.

## Session 19: `application_state.cc` — the top-level Application lifecycle state machine (6/6 decompiled)

`application_state.cc` was `bruce-decompile-status.md`'s #3 cheap-win target (1,956 remaining bytes, 0/6), and the doc's own session-18 note flagged it as "a natural pairing with `state_machine.cc`" since two of its functions were already known to call `state_machine__600849a4` directly. All 6 attributed functions are now decompiled (`analysis/decomp/application_state__*.c`), confirming the guess: this file is a **second, independent concrete instantiation** of the generic HSM engine documented above — not the BLE-adapter/pairing-mode one (`state_machine__600df264`'s territory), but a higher-level **"Application" boot/lifecycle state machine** that owns power-on/reboot-reason handling, shutdown, thermal events, and haptic-pattern feedback.

| Function | Bytes | Role |
|---|---:|---|
| `application_state__6005b8dc` | 770 | **The public entry point** — `ApplicationState(obj, event)`. No static caller found this session (plausibly reached through a vtable, like the adapter/GATT dead ends elsewhere in this project). Event `0` delegates to `application_state__6005b1c0` (below, boot/reboot-reason handling); a 14-way switch (events `0`–`0xd`) otherwise covers: `2` = enter a low-power/throttled mode (releases a wakelock); `4` = a partition-table-failure path (two distinct logged outcomes); `5`/`9`/`10` = plain state transitions; `6` = a transition with a secondary sub-flag; `7` = clears a flag and fires an alert-shaped call (`FUN_600d4e64`); `8` = **the shutdown/power-off path** (`FUN_6005bdac`), with a narrow-window (within 10s of boot) recovery fallback if a synchronous hardware handshake (`thunk_EXT_FUN_00001ea4`, 200ms timeout) fails; `0xb` = a charger/battery-shaped query (`FUN_6005acf4`) picking between two transitions; `0xc` = thermal (`thermal__6005d1e4`, `thermal.cc`); `0xd` = **the critical/fatal path** — plays haptic pattern `0xd` directly, then transitions to state `0x12`. After the switch, unconditionally: records a session/usage event via `application_state__6005ad74` (below), pokes an unidentified sink (`FUN_600df0f0`), arms a per-event watchdog-style timeout (`FUN_60076400(...)+0x3fc`), and — if `FUN_600dffe8(obj+8, event)` reports a change — **posts into the OOBE gate documented above, `state_machine__6008099c`**, closing that doc's "only caller found" open thread. |
| `application_state__6005b1c0` | 552 | **Boot/reboot-reason dispatcher.** Calls `reboot_reason__60059f98` (`reboot_reason.cc`) to fetch why the device last reset, stores the reason/sub-code into the object, and switches on it: case `1` reads config key `0x18` (via `FUN_600d382e`, one of `keys.cc`'s per-type getter/formatters per `bruce-misc-functions.md` — **ties this file directly to the already-documented typed key-value store**) and on a fresh/first-boot condition fires two usage-telemetry events (`thunk_FUN_60059eb8`, event types `2`/`0`) plus a haptic pattern (`FUN_6005f120(5)`); case `2` reads key `0x27` similarly; case `3` transitions straight to state `0`; case `5` (OOBE-adjacent) calls `application_state__6005b150` (below) to decide between two transitions; case `6` transitions to state `0x10`; default checks a hardware status bit (battery/charger-shaped) and either boots normally (state `0`) or routes to an error state (`0xf`) via `FUN_600678e0`. Every path ends by calling **`state_machine__600849a4`** — the generic engine's public post-event entry point documented above — confirming this object really is a `state_machine.cc` instance. |
| `application_state__6005b150` | 102 | **First-boot-for-this-build check.** Reads config key `0x28` (`FUN_600d382e`) and compares it against `info__6006180c()` (`info.cc`, still undecompiled) — almost certainly "does the persisted build/version marker match the currently-running build," i.e. detects a just-flashed/first-boot-of-new-firmware condition, gating some of `6005b1c0`'s OOBE-adjacent transitions above. |
| `application_state__6005b850` | 114 | **State setter.** Derives an expected/current-state value from a small lookup table (`DAT_6005b8c4`, indexed by `FUN_600d3e60()`), and — only if it actually differs from the object's stored state — logs the transition (`"... -> ..."`-shaped trace) and calls `application_state__6005b794` (below) to fire the associated haptic feedback. Gates the haptic side-effect on a real state change rather than firing every call. |
| `application_state__6005b794` | 168 | **Haptic-pattern dispatcher.** Switches the object's current-state field into a `gotham_patterns__600670f4(patternId)` lookup (`gotham_patterns.cc`) feeding `pattern_player__6007f8e4`/`FUN_6005ac84` (`pattern_player.cc`/`.h`) — confirming each Application-level state has an associated haptic pattern (pairing/connect, error, low-battery-shaped, etc. — exact pattern-ID semantics not decoded, `gotham_patterns.cc` itself is still undecompiled). |
| `application_state__6005ad74` | 250 | **Session/usage-event persistence helper**, called unconditionally at the end of `6005b8dc`. Writes one or two small records via `FUN_600d3df4` (still undecompiled; not part of `keys.cc`'s API, a distinct persistence/telemetry sink) keyed by small integer IDs (`1`/`2`/`4`) alongside `iVar1`(context pointer)/size pairs — shape consistent with a boot-session or usage-analytics log, not confirmed further. |

**Concrete state/event names still not recovered** (same caveat as the generic-engine section above — no adjacent string table for the numeric IDs), but this session substantially sharpens the picture `bruce-state-machine.md`'s "Open" section originally asked for: the Application state machine's initial state is chosen from the **reboot reason** (normal power-on vs. crash vs. low-battery-forced-off vs. OTA-update-triggered, per `firmware_image_upload.cc`'s `bruce-misc-functions.md` write-up, which fires the same `thunk_FUN_60059eb8` event-tag call this file uses before its own reset-and-wait loop), and every state transition drives both a haptic pattern (`gotham_patterns.cc`/`pattern_player.cc`) and a watchdog-style per-state timeout. This is very likely the top-level orchestrator tying together `wakelock.cc`, `thermal.cc`, `reboot_reason.cc`, and the haptic-feedback subsystem — a good next cluster (`gotham_patterns.cc`, `pattern_player.cc`, `info.cc`) if this thread gets picked up again.

## Session 22: `gatt_manager_task.cc` — the OOBE handler task, closing the "gatt_manager_task__60080cdc" loose end (4/4 decompiled)

`gatt_manager_task.cc` was `bruce-decompile-status.md`'s §3a rank-1 cheap-win target (518 remaining bytes, 0/4). All 4 attributed functions are now decompiled (`analysis/decomp/gatt_manager_task__*.c`), closing the loose end the top of this doc flagged: `state_machine__600df264` calls `gatt_manager_task__60080cdc` by name to spin up "BLE services" when the adapter transitions into an active/discoverable state, and this session found what that call actually does. Despite the filename, the object it constructs is a leaked-string-confirmed **OOBE (out-of-box-experience) handler task**, not a generic "GATT manager" — thread name `"gatt_mgr_task"`, log line `"OOBE task runnable started."`, and it dispatches `OobeRequest`-typed messages (`"Received uninitialized OobeRequest!"` on a malformed one).

| Function | Bytes | Role |
|---|---:|---|
| `gatt_manager_task__60080cdc` | 258 | **The lazy-singleton "get or create" entry point** — the exact function `state_machine__600df264` calls. Mutex-guarded: if the singleton already exists, returns it and bumps a refcount (`FUN_60074ec8`); otherwise allocates a large (`0x222c`/8,748-byte) object, constructs it (`gatt_manager_task__60080b24`, below), wraps it in a small intrusive-refcounted "cell" (vtable `PTR_PTR_60080de8`, refcount fields preset to 1/1 — the same refcounted-object idiom `bruce-itcm.md` documents elsewhere), and spawns the task thread (`thunk_EXT_FUN_00001680`, named `"gatt_mgr_task"` via `FUN_6010177a`). On thread-start failure, logs `"Failed to start oobe handler task: "` with the numeric error and returns a null pair instead. |
| `gatt_manager_task__60080b24` | 108 | **The object constructor.** Zeroes/initializes fields, sets up a 10-slot, 16-byte-stride message queue (`queue__600c9de4(10, 0x10, ...)`) — the `OobeRequest` mailbox the task loop below reads from — and, gated on a config flag, logs an additional init trace. |
| `gatt_manager_task__60080bcc` | 122 | **The task body**, i.e. what `"gatt_mgr_task"` actually runs. Sets a running flag, logs `"OOBE task runnable started."`, then loops indefinitely: blocks on the message queue (`thunk_EXT_FUN_00006d2c`, no timeout) for a `{msgType, resultPtr, semaphore}`-shaped record, dispatches `msgType==1` to `FUN_60080ba4` (still undecompiled — the actual OOBE-step handler), logs `"Received uninitialized OobeRequest!"` for `msgType==0`, writes the result byte back through the caller-supplied pointer if given, and signals a semaphore/notification (`FUN_60101832`) if one was passed. |
| `gatt_manager_task__60080af8` | 30 | Small helper: sets a vtable-shaped field pair and delegates to `FUN_600cc160` (still undecompiled) — shape-consistent with a base-class sub-object initializer, not independently interesting. |

**Net:** `gatt_manager_task.cc` is the **OOBE (out-of-box-experience) request-handling task** — a lazily-constructed, refcounted FreeRTOS task/object pair, started and torn down by the BLE-adapter pairing/discoverability state machine (`state_machine__600df264`) exactly when the controller becomes connectable, and driven by an `OobeRequest`-typed mailbox whose actual per-request logic (`FUN_60080ba4`) wasn't chased this session. This, plus the naming overlap, is a plausible (not confirmed) tie to `bruce-bta-stack.md`'s new `activation_sequence.cc` section (session 22, below) — both are GATT-adjacent and OOBE/setup-flow-shaped, though no direct call edge between the two files was found.

## Open

- Concrete state-id/event-id names for `state_machine__600805e4`'s transition table (0–6 states, 0–7 events) — **`application_state.cc` (session 19, above) turned out to be a *different* concrete instantiation (the Application lifecycle machine, not the BLE-adapter/pairing one this table belongs to), so it doesn't directly name these IDs.** Still needs either a manual Ghidra pass or a fresh string-table lead specific to `adapter.cc`'s pairing-mode state machine.
- The per-state subclass vtables (concrete `onEnter`/`onExit`/`handleEvent` overrides) — not chased; the generic engine's shape is confirmed but no specific state's *behavior* (beyond the one concrete `600df264` "apply adapter state" instantiation) has been read.
- `tasks__600ca4ac`-style loose ends aside, two callees referenced here remain undecompiled and could sharpen this further: `FUN_600e002e`/`FUN_600e008a` (the init-time hooks called by `state_machine__600848bc`) and `FUN_600e00ca` (the event-queue-full overflow handler in `state_machine__600849a4`) — all three live in the same `0x600ecb72`–`0x6013d4e4` unmapped run (`bruce-decompile-status.md` §3b run #2, still the largest still-mostly-unmapped range) as several of the log-buffer-framework functions, reinforcing that run as a mixed bag worth a dedicated sweep.
- `gatt_manager_task.cc`'s actual per-`OobeRequest` handler, `FUN_60080ba4`, is still undecompiled — the natural next hop to see what the OOBE flow actually does step by step.
